## 1. Vendor-backed transfer boundaries (retrieved 2026-09-28 UTC)

| Mechanism | Supported scope and boundary |
|---|---|
| Elementor **website template / export kit** | From **Elementor → Editor → Home → Tools → Website Templates → Export**, choose **Content** (pages, posts, CPTs, menus, taxonomies and media), **Templates** (saved/Theme Builder site parts and global widgets), **Settings & Configurations** (global colors/fonts, theme style, layout, lightbox, background, active experiments; plan-dependent custom fonts/icons/code and theme export), and **Plugins**. Export as ZIP for file-based import. Options vary by subscription; choosing *save media to cloud* precludes ZIP export; granular content selection is plan-dependent. From the same Website Templates tool, import a ZIP and select Templates, Content, Site Settings. Plugin selection is not a substitute for independently installing/authorizing dependencies. [Elementor import/export](https://elementor.com/help/import-and-export-elementor-website-templates/). Elementor documents classes/variables as included by default in current settings export, with selective export possible; verify availability in the installed version. [Elementor classes/variables](https://elementor.com/help/how-to-export-and-import-variables-and-classes/). |
| Individual templates | Saved templates may be exported/imported as JSON/ZIP; Theme Builder site parts have JSON export/import. This transfers *a template*, not an entire site's pages, global settings, plugin installation or WordPress options. Check display conditions on destination; some single-page templates apply only to **Default** page layout, not Canvas/Full Width. [Template library](https://elementor.com/help/template-library/), [Theme Builder](https://elementor.com/help/the-elementor-theme-builder/), [single-page site part](https://elementor.com/help/single-page-site-part/). |
| WordPress WXR/XML | WordPress/WP-CLI export contains authors, terms, posts, comments and attachment **records**, but **not** site options or attachment file bytes. Import requires the WordPress Importer (including for `wp import`); remote attachment fetch is conditional on the source being available. Treat WXR as an *optional, sanitized supplement* for WordPress content not carried by the kit, **never** as a second import of the same pages/templates. [WP-CLI export](https://developer.wordpress.org/cli/commands/export/), [WP-CLI import](https://developer.wordpress.org/cli/commands/import/), [WordPress Multisite migration tutorial](https://developer.wordpress.org/advanced-administration/multisite/sites-multisite/). |
| URLs and migration | No guarantee that every embedded URL is portable. Check WordPress Address/Site Address; after migration run Elementor **Replace URL** from old origin to destination when references persist, then **Clear Files & Data**/regenerate CSS and clear caches. Audit image/font/background and internal links; do not run naive SQL/text replacement on serialized data. [Elementor site migration](https://elementor.com/help/site-migration/), [URL change](https://elementor.com/help/i-changed-the-url-of-my-website-and-elementor-does-not-work-anymore/). |
| Dependencies and incomplete bindings | Elementor warns that imported kits may still lack connections for menus, site name/logo, categories, popups and other dependencies. Reconnect/check manually on the clean destination. Theme Builder is a Pro capability; Pro widgets need an installed, active, authorized Pro on the target, not just imported JSON. [Customize a kit](https://elementor.com/help/customizing-an-elementor-site-kit/), [Theme Builder](https://elementor.com/help/the-elementor-theme-builder/), [install Pro](https://elementor.com/help/installing-elementor-pro/). |
| Forms, custom code and secrets | A form *layout* may travel with its page/template; **do not assume** submissions, recipients, integrations, webhook URLs, API keys, SMTP, or action bindings transfer safely/correctly. Submissions are visitor data managed/exported separately; integrations may require API keys. Elementor Pro Custom Code can be included in plan-dependent settings export and has display conditions; it does not support PHP. **Disable/exclude and review any custom code before exporting; never ship secrets/tracking via a kit.** Recreate approved form delivery/integration and conditions privately, then use synthetic test entries. [Form submissions](https://elementor.com/help/form-submissions/), [form integration keys](https://elementor.com/help/can-i-integrate-elementor-to-my-email-marketing-service/), [custom code](https://elementor.com/help/custom-code-pro/), [import/export](https://elementor.com/help/import-and-export-elementor-website-templates/). |

A vendor kit is **not a complete DB backup**, license transfer, or guarantee of URL/media/plugin/option portability. Import to a **new/empty installation**: Elementor warns kits may overwrite/append existing content. [Elementor kit import](https://elementor.com/help/apply-selected-parts-kit/). Place raw downloads in ignored `reconstruction/incoming/`; do not commit an uninspected ZIP (it could embed plugin/theme payloads, personal data, media, custom code or endpoints). Promote only an audited, clean-import-tested artifact to `reconstruction/exports/`. Never assume that Pro code is absent merely because the export dialog says “Plugins.”

## 2. Canonical ownership and choice

**Chosen: A (official Elementor website-template ZIP) + separately version-controlled theme/code + this ordered rebuild contract.** The kit is the canonical *Elementor-editable design/content/settings snapshot* once a sanitized, inspected ZIP can actually be exported and re-imported. Git is the canonical store for our own theme/code, non-secret configuration, tests, this contract, artifact manifest and only approved small synthetic/demo assets. A kit saved solely in a personal/cloud library is **not** canonical. **D (sanitized WXR) only if a real clean-import pilot shows missing required non-Elementor WordPress content**; record exactly which posts/terms it owns and import once. **B (individual JSON templates) is for selective repair/reuse**, not a complete canonical site; it omits site-wide settings/pages/menus. **C (raw database dump) is rejected as canonical**: environment URL/option coupling, unreviewable diffs, credentials and personal data risk. A private operational backup may exist outside Git but cannot replace the portable contract.

**Environment/WordPress owned, never Git:** host/domain and HTTPS, DB credentials, salts, admin accounts/passwords, Elementor Pro package/account/license activation, SMTP and form-routing secrets, real submissions, analytics/verification secrets, environment-specific URL/site identity and settings, caches and backups. Keep exact version *numbers* in Git after verifying them; no keys or host access details. Configuration changed in WordPress must be either captured in an inspected artifact or recorded as an explicit rebuild step. Never depend on an agent's private database.

**Media:** small licensed, original, synthetic/demo assets may be Git-owned with attribution/manifest/checksum and importer mapping when needed. Real/large production media belongs in a separately controlled WordPress Media Library/asset store with a documented source, license and restoration path; a WXR attachment record alone is insufficient. No PHI or customer media. For a kit, select ZIP-compatible media mode, inspect its contents and verify every asset survives re-import. If media must stay outside Git, list it as an explicit environment prerequisite, not “reconstructable from Git” until access/relink is documented. Inspect SVGs before allowing unfiltered upload. **No actual kit/WXR/media exists in this repository yet.**
